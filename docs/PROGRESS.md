## 2026-08-21 — Фаза 1: База данных и архитектура

**Сделано:**
- Изменения Фазы 0 закоммичены и запушены в GitHub.
- Создана миграция `supabase/migrations/20260821000000_phase1_schema.sql`:
  все 8 таблиц из раздела 8 AGENT_INSTRUCTIONS.md (profiles, markers,
  marker_zones, reactions, messages, reports, live_locations,
  admin_actions) + расширение PostGIS + индексы.
- Включён Row Level Security везде:
  - свой профиль/метки/зоны — видит и меняет только владелец;
  - метки и зоны видны всем авторизованным (иначе карта бесполезна);
  - сообщения видят только участники переписки;
  - жалобы видит автор и модераторы/админы;
  - **live_locations**: включить показ себя может только подтверждённый
    18+; чужие позиции видны только пользователям 18+ и только тем,
    кто сам включил показ; по умолчанию всё выключено (opt-in);
  - забаненные не могут создавать метки, реакции, сообщения;
  - роль (user/moderator/admin) нельзя поменять самому себе.
- Добавлены служебные поля сверх ТЗ: role, banned у профилей; date_of_birth;
  мягкое удаление (deleted) у меток — понадобится модерации.

**Как проверить:**
- Открыть файл миграции в GitHub и убедиться, что он на месте.
- Применить миграцию в Supabase (SQL Editor → вставить содержимое файла
  целиком → Run), затем в Table Editor увидеть 8 новых таблиц.

**Осталось / известные проблемы:**
- Исправления миграции после ошибок:
  1) убран запрещённый WITH CHECK из SELECT-политики сообщений;
  2) предотвращена бесконечная рекурсия RLS в политике профиля через
     security-definer функцию my_profile();
  3) убран опасный блок DROP TABLE CASCADE из начала файла. Именно он
     вызывал deadlock (40P01), когда Supabase одновременно обновлял
     структуру базы. Миграция больше не удаляет таблицы, данные или
     триггеры.
- Файл проверен: все SELECT-политики используют только USING, а WITH CHECK
  используется только для INSERT/UPDATE.
- После deadlock (40P01) убран DROP TABLE CASCADE и добавлены явные BEGIN/COMMIT:
  миграция не удаляет данные и применяется атомарно.
- После ошибки `42P07: relation "profiles" already exists` миграция
  переделана в повторно запускаемую: все 8 таблиц используют IF NOT EXISTS,
  индексы — IF NOT EXISTS, политики заново выставляются через временную
  служебную функцию, а триггер создаётся только если его ещё нет. Теперь
  запуск можно повторить поверх уже частично созданной схемы без ручного
  удаления таблиц.
- Миграция не завершилась целиком в живой базе: по ошибке 42P07 уже
  существует как минимум таблица profiles, поэтому следующий запуск должен
  продолжить настройку поверх существующей схемы. Терминал среды не получает
  SUPABASE_ACCESS_TOKEN, поэтому применение пока выполняется вручную через
  Supabase SQL Editor.
- Автоочистка истёкших меток (TTL-cleanup) будет добавлена в Фазе 4.
- Профили видны только владельцу — для «людей рядом» и сообщений позже
  потребуется открыть чтение публичной части профиля (спросить заказчика).

**Нужно от заказчика:**
- Применить миграцию: открыть панель Supabase → SQL Editor → New query,
  вставить весь текст из `supabase/migrations/20260821000000_phase1_schema.sql`,
  нажать Run. Либо перезапустить воркспейс Freebuff — тогда попробую
  применить автоматически.
