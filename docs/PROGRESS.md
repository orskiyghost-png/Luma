## 2026-08-22 — Фазы 6–7: антиспам, жалобы и панель модерации

**Фаза 6 — антиспам и жалобы:**
- Серверное ограничение частоты действий: таблица `rate_limits` + функция
  `check_rate_limit(action, max, window)` (security definer, скользящее окно).
  Работает и на бессерверном хостинге — счётчик в БД. Подключено к:
  создание метки (5/мин), отправка сообщения (20/мин), новая беседа (10/час),
  жалоба (10/час). Проверено: 6-й вызов в окне возвращает false.
- Жалобы через функцию `submit_report(target_type, target_id, reason)`:
  валидация типа, запрет жалобы на себя, анти-дубликат в пределах суток.
  Клиентский компонент `components/report-dialog.tsx` (выбор причины + текст).
  Кнопки «Пожаловаться» добавлены в попап метки и в шапку чата (на профиль
  собеседника). Серверное действие — `app/actions/reports.ts`.
- Задел под Cloudflare Turnstile: `lib/security.ts` (`verifyTurnstile`,
  `isTurnstileEnabled`). Если ключ капчи не задан — не блокирует; включается
  добавлением ключей без правки кода.

**Фаза 7 — панель модерации/админа:**
- Все действия модерации — через security-definer RPC, которые сами проверяют
  роль вызывающего и пишут запись в `admin_actions`. Прямого доступа к чужим
  данным у клиента нет. Функции: `admin_list_reports`, `admin_set_report_status`,
  `admin_delete_marker`, `admin_set_ban`, `admin_set_role` (роль меняет только
  admin), плюс `current_is_staff` / `current_is_admin`.
- Экран `/admin` (server) с фильтром по статусу жалоб и клиентским
  `admin-reports.tsx`: перевод жалобы в работу/решено/отклонено, удаление
  метки, бан/разбан автора, назначение модератора (для админа). Доступ к
  `/admin` защищён в middleware, страница дополнительно редиректит не-персонал
  на `/map`. Ссылка «Модерация» в профиле видна только персоналу.
- Проверено сквозным тестом (`scripts/smoke-phase67.sh`): жалоба и дубликат,
  запрет доступа не-персоналу (forbidden), список жалоб у модератора, удаление
  метки, бан → забаненный не может ставить метки (RLS 403), запрет смены роли
  для не-админа, срабатывание rate-limit. Тестовые данные удалены.

**Как назначить первого администратора** (нужно один раз, вручную):
в Supabase → SQL editor выполнить, подставив email владельца:
`update public.profiles set role='admin' where user_id=(select id from auth.users where email='ВАШ_EMAIL');`
После этого в профиле появится кнопка «Модерация».

**Осталось:** подтверждение 18+ и страницы Политики/Условий (Фаза 8),
опциональные «люди рядом» только для 18+ (Фаза 9), заглушка подписки Stripe
(Фаза 10), финальная полировка дизайна (Фаза 11), предзапусковый чек-лист
(Фаза 12).

**Билд:** `tsc --noEmit` и `next build` проходят; новые маршруты `/admin`
собираются.

## 2026-08-22 — Фаза 4 (фикс 2): сохранение данных и выбор точки

**Причины жалоб:** запасной iframe-карте нельзя было передать касание в
приложение; запрос меток выполнялся до показа карты; координаты геолокации
жили только в памяти; сохранение профиля не показывало полезную причину отказа.

**Сделано:**

- Запрос активных меток перенесён после первого показа карты — медленный
  Supabase больше не блокирует открытие экрана.
- В запасном режиме добавлен прозрачный слой выбора точки поверх карты:
  касание переводится в координаты видимой области, выбранная точка отмечается
  красным указателем, затем открывается форма публикации.
- В запасном режиме уже созданные метки теперь отображаются поверх карты.
- После явного разрешения геолокации координаты сохраняются локально на
  устройстве и в личной строке `live_locations` в Supabase. `sharing_enabled`
  остаётся `false`, поэтому координаты не публикуются другим пользователям.
- Сохранение профиля выполняется через прямое обновление существующей строки;
  если строки нет, она создаётся. Ошибки RLS/отсутствующей таблицы получают
  понятный текст вместо молчаливого общего сбоя.
- Запасной режим включается через 3 секунды вместо 5, чтобы не ждать карту
  при медленной сети.
- Typecheck проходит; Preview: `/` и `/auth` → 200, защищённые `/map` и
  `/profile` для гостя → 307; диагностика Supabase/MapTiler без ошибок.

**Как проверить:**
1. Обновить карту. Она должна открыться быстрее.
2. Нажать «📍 Моё место» → «Показать моё место». После ответа появится
   «Местоположение сохранено только для вашего аккаунта».
3. Нажать «＋ Поставить метку».
4. Нажать на нужную точку карты — красный указатель должен остаться именно
   в месте касания. Заполнить текст и нажать «Опубликовать».
5. Открыть профиль, изменить имя/город/«О себе», нажать «Сохранить профиль».
   Должно появиться «Профиль сохранён.»; при проблеме будет объяснение.

**Осталось / известные проблемы:**
- В fallback-карте OSM нельзя отслеживать последующее перемещение внутри
  iframe после выбора; точка выбирается корректно по текущему изображению карты.
- Нормальный режим MapLibre остаётся основным и даёт точную географическую
  привязку при клике.

**Нужно от заказчика:** повторно проверить три сценария выше; присылать нужно
только текст ошибки, если она появится.

## 2026-08-22 — Фаза 4 (фикс): кнопка метки видна на телефоне

**Причина проблемы:** кнопка «＋ Метка» выводилась только при `mode ===
"webgl"`. На телефоне карта открылась в запасном режиме OSM, поэтому кнопка
полностью исчезла, хотя карта была видна.

**Сделано:**

- Кнопка переименована в понятную **«＋ Поставить метку»** и теперь всегда
  видна рядом с кнопкой геолокации.
- На узком экране нижняя панель переносится и сжимается без выхода кнопок за
  границы экрана.
- В WebGL-режиме сценарий прежний: нажать кнопку → нажать место на карте →
  выбрать категорию и написать текст.
- В запасном OSM-режиме iframe нельзя обработать кликом из приложения, поэтому
  кнопка автоматически выбирает центр текущего экрана. Если сначала нажать
  «Моё место», метка будет создана в найденной точке пользователя.
- Исправлена подсказка режима размещения: она корректно учитывает координаты
  около нулевой широты.
- Typecheck проходит; Preview: `/` и `/auth` → 200, защищённые `/map` и
  `/profile` для гостя → 307.

**Как проверить:**
1. Открыть карту на телефоне — внизу должны быть две кнопки: «📍 Моё место» и
   «＋ Поставить метку».
2. В обычном режиме карты нажать «＋ Поставить метку», затем нажать на карту.
3. В запасном режиме сначала при необходимости нажать «Моё место», затем
   «＋ Поставить метку»: форма откроется для центра карты.
4. Выбрать категорию, написать текст и нажать «Опубликовать».

**Осталось / известные проблемы:**
- В OSM-fallback нельзя выбрать произвольную точку касанием iframe; сейчас
  метка ставится в центр, чтобы функция не исчезала и оставалась рабочей.
- Rate limiting и автоматическая очистка истёкших меток будут добавлены в
  следующих фазах.

**Нужно от заказчика:** проверить кнопку «＋ Поставить метку» на телефоне.

## 2026-08-22 — Фаза 4: метки на карте

**Сделано:**

- **Server Actions** (`app/map/actions.ts`): создание (`addMarker`), удаление
  (`deleteMarker`) и загрузка активных меток (`getActiveMarkers`). Удаление —
  мягкое (поле `deleted`), только владелец может удалить свою метку.
- **TTL по категориям:** ДТП — 4 ч, Полиция — 2 ч, Гуляем — 6 ч, Другое — 12 ч.
  Обоснование: экипажи ДПС меняют позицию часто, аварии рассасываются за
  несколько часов, прогулка длится до вечера, своя категория — с запасом.
- **UI создания метки:** кнопка «＋ Метка» внизу карты, после нажатия —
  подсказка «нажмите на карту», клик открывает форму с выбором категории
  (4 кнопки) и полем текста (до 280 символов). Снизу показан TTL.
- **Отображение меток:** на карте — цветные кружки с иконками по категориям
  (🚗 ДТП, 🚔 Полиция, 🎉 Гуляем, 📌 Другое). При клике — попап с текстом,
  временем публикации и остатком TTL. Владелец видит кнопку «Удалить метку».
- Метки загружаются на сервере при открытии страницы (быстрый первый рендер),
  затем обновляются на клиенте после создания/удаления.
- Работает только на WebGL-карте; OSM-fallback предупреждает, что метки не видны.
- Typecheck проходит; Preview: `/`, `/auth` → 200; `/map` и `/profile` → 307.

**Как проверить:**
1. Войти в аккаунт → открыть карту.
2. Нажать «＋ Метка» → нажать на любое место → выбрать категорию → написать
   текст → «Опубликовать». Метка появится в этой точке.
3. Кликнуть по метке — открывается попап с текстом, временем, TTL.
4. Нажать «Удалить метку» — метка исчезает.
5. Создать несколько меток с разными категориями.

**Осталось / известные проблемы:**
- В OSM-fallback режиме метки не отображаются.
- Автоматическая очистка истёкших меткок (cron/edge function) будет добавлена
  позже, пока RLS-политика `markers_select_active` скрывает их в выдаче.
- Rate limiting на создание меток добавится в Фазе 6.

**Нужно от заказчика:** проверить создание и удаление меток на карте.

  - свой профиль/метки/зоны — видит и меняет только владелец;
  - метки и зоны видны всем авторизованным (иначе карта бесполезна);
  - сообщения видят только участники переписки;
  - жалобы видит автор и модераторы/админы;
  - **live_locations**: включить показ себя может только подтверждённый
    18+; чужие позиции видны только пользователям 18+ и только тем,
    кто сам включил показ; по умолчанию всё выключено (opt-in);
  - забаненные не могут создавать метки, реакции, сообщения;
  - роль (user/moderator/admin) нельзя поменять самому себе.
- Добавлены служебные поля сверх ТЗ: role, banned у профилей; date_of_birth;
  мягкое удаление (deleted) у меток — понадобится модерации.

**Как проверить:**
- Открыть файл миграции в GitHub и убедиться, что он на месте.
- Применить миграцию в Supabase (SQL Editor → вставить содержимое файла
  целиком → Run), затем в Table Editor увидеть 8 новых таблиц.

**Осталось / известные проблемы:**
- Исправления миграции после ошибок:
  1) убран запрещённый WITH CHECK из SELECT-политики сообщений;
  2) предотвращена бесконечная рекурсия RLS в политике профиля через
     security-definer функцию my_profile();
  3) убран опасный блок DROP TABLE CASCADE из начала файла. Именно он
     вызывал deadlock (40P01), когда Supabase одновременно обновлял
     структуру базы. Миграция больше не удаляет таблицы, данные или
     триггеры.
- Файл проверен: все SELECT-политики используют только USING, а WITH CHECK
  используется только для INSERT/UPDATE.
- После deadlock (40P01) убран DROP TABLE CASCADE и добавлены явные BEGIN/COMMIT:
  миграция не удаляет данные и применяется атомарно.
- После ошибки `42P07: relation "profiles" already exists` миграция
  переделана в повторно запускаемую: все 8 таблиц используют IF NOT EXISTS,
  индексы — IF NOT EXISTS, политики заново выставляются через временную
  служебную функцию, а триггер создаётся только если его ещё нет. Теперь
  запуск можно повторить поверх уже частично созданной схемы без ручного
  удаления таблиц.
- Миграция не завершилась целиком в живой базе: по ошибке 42P07 уже
  существует как минимум таблица profiles, поэтому следующий запуск должен
  продолжить настройку поверх существующей схемы. Терминал среды не получает
  SUPABASE_ACCESS_TOKEN, поэтому применение пока выполняется вручную через
  Supabase SQL Editor.
- Автоочистка истёкших меток (TTL-cleanup) будет добавлена в Фазе 4.
- Профили видны только владельцу — для «людей рядом» и сообщений позже
  потребуется открыть чтение публичной части профиля (спросить заказчика).
